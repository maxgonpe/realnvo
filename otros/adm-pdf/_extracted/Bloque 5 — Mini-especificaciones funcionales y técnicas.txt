1. Propósito del bloque
Este bloque completa el módulo de facturación y pagos mediante las funciones de:
• Control de pagos con saldo disponible.
• Identificación de excedentes.
• Vinculación de pagos con movimientos bancarios.
• Seguimiento de acciones de cobranza.
• Registro de compromisos de pago.
• Alertas por vencimiento, promesas incumplidas y falta de respuesta.
• Antigüedad de saldos.
• Reportes y exportaciones.
• Pruebas integrales del módulo.
Al finalizar este bloque, el sistema podrá responder:

¿Qué pagos todavía tienen dinero sin aplicar?
¿Qué pagos aparecen efectivamente en la cartola?
¿Qué facturas están próximas a vencer?
¿Qué facturas están vencidas?
¿Qué gestiones de cobranza se han realizado?
¿Qué compromisos de pago no se cumplieron?
¿Cuánto debe cada cliente?
¿Cuál es la antigüedad de esa deuda?

4. Tres saldos diferentes que deben distinguirse
Dentro del módulo existen tres conceptos monetarios diferentes.

4.1 Saldo de la factura
Saldo factura
= total factura
− aplicaciones de pago válidas
Indica cuánto continúa debiendo el cliente.

4.2 Saldo sin aplicar del pago
Saldo sin aplicar
= monto del pago
− aplicaciones activas a facturas
Indica cuánto dinero del pago todavía no ha sido distribuido entre facturas.

4.3 Saldo bancario pendiente del pago
Saldo bancario pendiente
= monto del pago
− aplicaciones bancarias activas
Indica cuánto del pago todavía no ha sido respaldado por movimientos de cartola.
Estos tres saldos pueden ser distintos.
Ejemplo:

Pago registrado:
Aplicado a facturas:
Vinculado con cartola:
Saldo sin aplicar:
Saldo bancario pendiente:

$1.000.000 CLP
$800.000 CLP
$600.000 CLP
$200.000 CLP
$400.000 CLP

El sistema no debe confundir distribución contable con conciliación bancaria.

3. Ajuste conceptual al modelo
La propiedad actual monto_aplicado suma todas las aplicaciones que no estén anuladas.
Se recomienda distinguir:

@property
def monto_distribuido(self):
"""
Total reservado o distribuido entre facturas,
incluyendo aplicaciones pendientes o especiales.
"""

@property
def monto_aplicado_valido(self):
"""
Total que efectivamente reduce deuda de facturas.
Solo aplicaciones con estado APLICADA.
"""

@property
def saldo_sin_distribuir(self):
return self.monto - self.monto_distribuido
Esto evita interpretar una aplicación PAGO_ERRONEO_FACTORING como pago válido de una factura,
pero impide que el mismo dinero sea reutilizado mientras se regulariza.

F009 — Vinculación con cartola bancaria
1. Objetivo
Relacionar un pago registrado con uno o más movimientos bancarios que demuestren su recepción
efectiva.
La Carta Gantt exige que un pago pueda conciliarse con uno o más movimientos.
Ejemplo:

Pago registrado:
Movimiento bancario A:
Movimiento bancario B:

$1.000.000 CLP
$600.000 CLP
$400.000 CLP

Resultado:

Pago bancariamente conciliado

10

2. Modelo utilizado
AplicacionMovimientoBancario
Con:

destino = PAGO_CLIENTE
pago_cliente = pago correspondiente
No se creará otra tabla de relación.

3. Dirección permitida
Un pago recibido por Extintores Real debe vincularse con movimientos:

INGRESO
Un pago informado como recibido directamente por una empresa de factoring no necesariamente
aparecerá en la cuenta bancaria propia.
En ese caso:
• El pago puede existir sin conciliación en la cuenta de la empresa.
• Su evidencia provendrá de información del factor.
• No debe forzarse una cartola propia inexistente.

4. Monto bancariamente conciliado
Se agregará a PagoCliente :

@property
def monto_conciliado_banco(self):
total = self.aplicaciones_bancarias.filter(
activa=True
).aggregate(t=Sum("monto"))["t"]
return total or Decimal("0.00")

@property
def saldo_por_conciliar_banco(self):
return self.monto - self.monto_conciliado_banco

@property
def estado_conciliacion_bancaria(self):
if self.monto_conciliado_banco <= 0:
return "NO_CONCILIADO"
if self.monto_conciliado_banco < self.monto:
return "PARCIAL"
return "CONCILIADO"
No es obligatorio persistir este estado en una primera versión; puede calcularse mediante consultas
anotadas.

5. Reglas de negocio
1. Solo se vinculan movimientos de ingreso.
2. El pago y el movimiento deben utilizar la misma moneda.
3. La suma bancaria no puede superar el pago.
4. La suma aplicada al movimiento no puede superar el movimiento.
5. Un movimiento puede cubrir varios pagos.
6. Un pago puede estar cubierto por varios movimientos.
7. Una vinculación puede ser parcial.
8. Un pago anulado no puede recibir aplicaciones.
9. Un movimiento excluido no puede utilizarse.
10. Un movimiento completamente conciliado no puede excederse.
11. Las aplicaciones no se eliminan físicamente.
12. Una reversa debe indicar motivo.
13. La fecha bancaria puede diferir de la fecha informada del pago.
14. Diferencias relevantes de fecha o monto deben generar advertencia.
15. La operación debe ser atómica.

6. Control del límite del pago
