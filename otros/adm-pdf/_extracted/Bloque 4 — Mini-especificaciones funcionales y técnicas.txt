técnicas
Facturación y cobranza: F001 a F007

1. Propósito del bloque
Este bloque construye las funciones principales para:
• Reutilizar los clientes existentes.
• Administrar contactos de facturación y cobranza.
• Registrar o importar facturas de venta.
• Consultar facturas.
• Calcular su estado de cobranza.
• Registrar pagos recibidos o informados.
• Distribuir un pago entre varias facturas.
• Permitir que una factura sea cubierta por varios pagos parciales.
• Actualizar saldos sin sobreaplicar pagos ni facturas.
• Preparar la integración posterior con cartolas bancarias y factoring.
Al finalizar este bloque, el sistema podrá responder:

¿Qué facturas tiene un cliente?
¿Cuánto se ha pagado?
¿Cuánto permanece pendiente?
¿Está vencida?
¿Qué pagos cubren la factura?
¿A qué facturas fue aplicado un pago?
¿El pago fue recibido por la empresa o por factoring?

4. Separación entre factura, pago y movimiento
bancario
Estos conceptos no deben fusionarse.

4.1 Factura
Representa la obligación de pago del cliente:

Cliente debe pagar $1.000.000

4.2 PagoCliente
Representa un pago recibido, informado o registrado:

Cliente pagó $700.000
El pago puede existir temporalmente sin estar asociado a una factura.

4.3 AplicacionPagoFactura
Indica cómo se distribuye el pago:

$500.000 → Factura A
$200.000 → Factura B

4.4 MovimientoBancario
Representa lo que efectivamente aparece en la cartola:

Ingreso bancario por $700.000

6. Ajustes principales detectados
6.1 Contactos múltiples
El modelo Cliente solo admite un contacto principal mediante campos simples.
Para facturación y cobranza se necesitan varios contactos:
• Administración.
• Contabilidad.
• Pago de proveedores.
• Compras.
• Responsable técnico.
• Representante legal.
Se propone crear ContactoCliente .

5

6.2 Estado de factura
NOTA_CREDITO aparece actualmente como estado documental de una factura.
Sin embargo, una nota de crédito es un documento relacionado, no un estado equivalente a “emitida” o
“anulada”.
La primera fase puede conservar el campo para no romper migraciones, pero la arquitectura correcta
es crear una entidad separada:

NotaCreditoVenta

6.3 Validación de montos
El modelo actual restringe que el total sea positivo, pero no valida explícitamente:

IVA = neto × tasa IVA
total = neto + IVA
Esta regla debe implementarse en formularios y servicios.

6.4 Estados persistidos
estado_cobranza se guarda en la base de datos, pero también se calcula.
Esto puede generar estados obsoletos si:
• Se aplica un pago.
• Se anula una aplicación.
• Se vence una factura durante la noche.
• Se crea o cierra una operación de factoring.
Debe existir un servicio único de actualización.

6.5 Validación mediante clean()
La lógica de AplicacionPagoFactura.clean() no se ejecuta automáticamente con cualquier
llamada a save() .
Las aplicaciones deberán crearse mediante servicios que llamen:

aplicacion.full_clean()
antes de guardar.

4. Cálculo monetario
Para una factura afecta:

IVA = redondear(neto × tasa_iva, 2)
total = neto + IVA
Para una factura exenta:

tasa_iva = 0
IVA = 0
total = neto
No debe confiarse exclusivamente en cálculos de JavaScript.
El backend debe recalcular y comparar.

6. Validaciones
1. El número es obligatorio.
2. El número no puede repetirse.
3. La fecha de vencimiento no puede ser anterior a la emisión.
4. El neto no puede ser negativo.
5. El IVA no puede ser negativo.
6. El total debe ser positivo.
7. El total debe coincidir con neto más IVA.
8. En una factura exenta, IVA debe ser cero.
9. El cliente debe estar activo.
10. La factura debe conservar el contacto utilizado.
11. El correo debe tener formato válido.
12. Una factura anulada no recibe nuevas aplicaciones.
13. Una factura con pagos no puede anularse sin reversar sus aplicaciones.
14. El número no podrá modificarse libremente después de tener pagos o factoring.
